Vision: AprilTag localizer + field EKF

Replay of a recorded match

The field EKF fuses tag fixes from the localizer with the camera’s visual-inertial odometry (VIO).

It replaced a node that judged each tag sighting through hand-tuned gates; now each fix is weighted by the covariance the localizer computed. The EKF predicts from the VIO odometry at about 400 Hz and corrects with each tag fix. Before the update, the tag pose is converted to the robot base through the camera mount, then carried forward to now with odometry. On the robot controller, WPILib’s pose estimator fuses the result with wheel odometry.

I wrote the EKF in Python first, then ported it to C++ to cut CPU load.

Details: state-estimation, perception-sqpnp

Replay: python state-estimation/replay/replay_field_ekf.py → a Python port of the C++ EKF tracks the recorded field pose to a median of 0.008 mm after the cold start (130 tag updates; 1 of 130 above the 95 % line of NIS, the normalized innovation squared).

Point cloud and localizer

The AprilTag localizer turns a camera image into the camera’s pose on the field, plus a 6x6 covariance.

With two or more tags in view, all corners are pooled, and OpenCV’s SQPnP (a perspective-n-point solver) seeds the camera pose. A weighted Levenberg–Marquardt (a least-squares refinement) step follows, and the covariance comes from a numeric Jacobian. With one tag, IPPE (OpenCV’s planar-target solver) returns both candidate poses of the flat square, and the covariance gains the spread toward the second pose. If the geometry is not observable, the pose is withheld instead of inventing a covariance.

The point cloud is the Odin camera driver’s own output, not my work. The localizer reads the same camera’s images; it started from a teammate’s port, and its pooled multi-tag solve and covariance are mine.

Details: perception-sqpnp

Replay: python perception-sqpnp/replay/replay_localizer.py → re-solving 178 pooled frames from the logged corners, which the node rounded to whole pixels, lands within a median 14.1 mm of the recorded pose; from unrounded corners reprojected from each tag’s logged pose, 0.48 mm.

Shoot on the move

A turret that keeps aiming while the robot drives, with shot compensation for the robot’s own velocity.

A ball fired from a moving robot keeps the robot’s velocity, so a shot table built for a standing robot is not enough. The compensation looks ahead to the release moment and splits the velocity into the part toward the target and the part across it. From that it sets a turret angle, a hood angle and a ball exit speed. An outer loop turns the angle error into a velocity command, which the motor controller’s own velocity loop tracks.

I wrote the turret’s aiming cascade and its shot compensation, with contributions from teammates.

Details: control/turret-2026

Replay: python control/turret-2026/replay/replay_shot_solution.py → the turret loop’s aim error and feedforward recompute from the 30 s log to within 0.0010° and 0.0005 V; tracking RMS 0.90° (in this clip the turret held a fixed field heading and shot compensation was off; the compensation law is shown as a counterfactual).

Whole-body control

Whole-body arm control

Instead of hand-written arm setpoints and state machines, a solver on the coprocessor decides how the whole robot moves.

The robot is a swerve chassis (each wheel drives and steers) with a three-joint planar arm: shoulder, telescope and wrist. A phase state machine runs DRIVE, APPROACH, TASK and RETRACT; APPROACH waits until the arm reaches its aim posture and the chassis its staging pose. On entering TASK, the goal is converted into the solver’s frame through the measured chassis pose and frozen, so it stays at one field point.

I wrote nearly all of both halves. One is a Python ROS 2 node that solves a quadratic program (QP) with the Placo library; the other is the robot’s joint executor. Gating TASK on arrival at the staging pose was validated on hardware; the goal freeze and the QP moving the chassis were simulation-only.

Details: control/wholebody-2026

Reaching a field-fixed goal from AprilTag localization

AprilTag fixes tell the robot where it stands, so the arm’s goal can be fixed on the field.

AprilTags are printed squares at known places on the field; a tag fix is a pose from one camera frame. The arm’s goals are poses fixed on the field, while the whole-body solver works in the robot’s own frame. Before TASK, APPROACH also requires the field pose to be fresh. In TASK, each QP step moves the end of the arm toward the goal within joint and speed limits.

I wrote the field EKF (extended Kalman filter), which turns the localizer’s tag fixes into the robot’s field pose; both are shown under Vision.

About the clip: I recorded this demo, where an AprilTag on the end of a stick moves near the robot and the arm follows it. This demo mode is not excerpted in the showcase repository.

Auto-tuning

A PID tuning bench for an arm joint, steered by a coding agent inside hard limits.

A blind grid or greedy search over an arm joint’s PID and feedforward gains tends to chase noisy minima into extreme values. The node sets gains, drives the joint through a test trajectory, scores the result, and aborts if anything looks unsafe. The agent decides which gain to sweep next, over what range, and when to stop, with a stated reason for every move. Each episode aborts to IDLE if the joint leaves its safe position band, the stator current (motor current) spikes, or the velocity reverses too often.

I wrote a ROS 2 node on the bench computer that runs the experiments, and the procedure a coding agent (Claude Code) follows. There is no language-model API client: the deterministic sweep stays in code that enforces the limits, and the agent points it.

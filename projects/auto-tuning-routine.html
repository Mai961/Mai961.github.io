Auto-tuning routine

Problem

Each arm joint’s position controller, PID plus feedforward gains, has to be tuned on a test bench. A blind grid or greedy search over the gains tends to chase noisy minima into extreme values.

What I built

I wrote a ROS 2 node on the bench computer that runs the experiments, and a written procedure that a coding agent (Claude Code) follows to steer them. The node sets gains, drives the joint through a test trajectory, scores the result, and aborts if anything looks unsafe. The agent decides which gain to sweep next, over what range, and when to stop, with a stated reason for every move. There is no language-model API client in the code: the deterministic sweep stays in code that enforces the limits, and the agent points it.

How it works

The agent sets one ROS parameter to a JSON directive and reads back a JSON result file. A sweep runs one episode per value and keeps the cheapest, scored on rise time, tracking error, overshoot, settling error and vibration. Each gain has a hard range declared on its ROS parameter, so the parameter server rejects an out-of-range value (kV and kA also travel on direct topics that do not re-check it). During every episode, a breach check aborts to IDLE if the joint leaves its safe position band, the stator current spikes, or the velocity reverses too often; an aborted episode scores infinity, so it can never win. When the agent is done, the gains go to a YAML file, and a human edits them into the robot’s configuration. A fork of the same bench was used to retune the turret’s loops.
